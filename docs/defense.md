# Подготовка к защите

## Короткое выступление

Мой проект называется LightKeeper. Это сервис учёта фонарей и аккумуляторов.
Тема удобна для небольшой системы: есть каталог, состояния оборудования
и записи обслуживания. Позже можно реализовать API, добавить PostgreSQL
и запускать компоненты в Docker Compose.

Сначала я добавил README, проектные заметки и план API. Затем отдельно
развивал каталог в `feature/catalog` и описание API в `feature/api-plan`.
Ветки позволяют изолировать изменения и объединить готовый результат в main.
В каждой ветке есть небольшие осмысленные коммиты.

Для демонстрации конфликта созданы `docs/usage` и `docs/description`.
Обе меняют одну строку назначения в README от общего предка. После
слияния первой ветки второе слияние остановилось с конфликтом. Я объединил
оба варианта назначения, убрал маркеры и завершил слияние отдельным коммитом.
В графе видны ответвления и точки слияния; merge-коммиты имеют двух родителей.

## Вопросы и ответы

| Вопрос | Ответ |
| --- | --- |
| Что хранит коммит? | Снимок дерева файлов, родителей, автора и сообщение. |
| Что такое ветка? | Подвижный указатель на коммит; при новых коммитах указатель сдвигается. |
| Зачем staging area? | Чтобы выбрать изменения, которые войдут в следующий коммит. |
| Что делает merge? | Объединяет истории; при расхождении создаёт коммит с несколькими родителями. |
| Зачем `--no-ff`? | Сохраняет отдельный merge-коммит даже при возможности fast-forward. |
| Почему получился конфликт? | Две ветки изменили одну строку относительно общего предка по-разному. |
| Чем merge отличается от rebase? | Merge связывает истории; rebase переносит коммиты на новую базу и меняет их хеши. |
| Как доказать исправление? | Показать `git-conflict.md`, два родителя merge-коммита и `--remerge-diff`. |
| Почему ветки не удалены? | В задании нужно показать минимум три ветки; сохранены все пять. |
| Приложение уже запускается? | Нет, эта контрольная точка посвящена Git; сейчас есть проектные файлы и примеры. |

## Что открыть преподавателю

1. Главную страницу публичного репозитория с README.
2. Список пяти веток.
3. Историю main и merge-коммит `fix: разрешить конфликт…`.
4. `git-conflict.md` и `docs/evidence/conflict-before.txt`.
5. Вкладку Insights → Network после публикации всех веток.

До защиты следует прочитать файлы и уметь повторить команды локально.
